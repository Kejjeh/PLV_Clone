## TL;DR

Cannot run the proposed test on the existing backfill panel for two
independent reasons:

1. ESPN's `recent_activity` (transactions) endpoint returns
   `ESPNInvalidLeague: League 24080 does not exist` for years 2024 and
   2025, even though `box_scores`/`teams` for those same years return
   normally. ESPN gates the `/communication/` endpoint to the *current*
   season only. Historical transactions are not retrievable.
2. The existing backfill panel (`predictions_history.csv`,
   `is_synthetic=True`, 141 rows across 2024-2025) was generated by
   `build_synthetic_calibration_panel.py`. Those projections are
   *roster-agnostic* — they use a Bayesian-shrunk season-to-date team
   average, not a Monday-roster rh3/rp3 sum. There is no
   "Monday roster" snapshot to update with mid-week add/drops in the
   synthetic rows.

Live 2026 panel: 9 actuals-backed rows, all from period 7 for a single
team. Far too few to fit any mid-week residual model.

VERDICT: `NEEDS_MORE_DATA`. Re-run this validation late 2026 once we
have ≥6 closed periods of *live* rh3/rp3-projected matchups whose
Monday roster + per-period `recent_activity` log are both captured.

The 141 synthetic rows do not represent a Monday-roster projection.
`build_synthetic_calibration_panel.py` explicitly documents this:

> What this validates: the win-probability mechanism (gap / sigma →
> normal CDF), independent of rh3/rp3 quality. NOT the rh3/rp3
> projection itself.

So even if 2025 transaction history *were* retrievable, applying
add/drop deltas to a team-average projection would be category-confused
— the projection has no concept of "which players are on the team."

Mean residuals are positive (projection under-shoots) but this is the

## What would unblock this

Need *both* of these in parallel from now on:

1. **Per-period Monday-snapshot roster capture.** The 2026 live
   pipeline already snapshots `my_projected_total` /
   `opp_projected_total` on Monday — extend to also persist the full
   roster list per team per period to a sidecar table
   (e.g. `data/outputs/matchup_rosters_history.csv`).
2. **Per-period transaction capture.** Run `recent_activity()` daily
   (it only retains current season), filter to that period's window,
   persist to `data/outputs/transactions_history.csv` keyed by
   `(period, team_id, event_date, action, player_id)`.

With ~6 closed live periods, the proposed test becomes runnable:
build `projected_total_initial` from the Monday roster, walk the
transactions chronologically updating it (add player's
remaining-week rh3/rp3 contribution; subtract dropped player's),
arrive at `projected_total_final`, compare residuals.

## Spec — minimum logging to ship now

Two ~30-line additions to `refresh_dashboards.py`:

```python
# A. Persist Monday roster per period
from app.espn_connector import get_all_teams
roster_snapshot = get_all_teams()
roster_snapshot['period'] = current_period
roster_snapshot['snap_date'] = today
roster_snapshot.to_csv(
    'data/outputs/matchup_rosters_history.csv',
    mode='a', header=not Path(...).exists(), index=False,
)

# B. Persist transactions daily (current season only — ESPN limitation)
from espn_api.baseball import League
acts = league.recent_activity(size=200)  # adjust size to span >24h
rows = [
    {'period': current_period, 'event_ts': a.date,
     'team_id': team.team_id, 'action': action, 'player_name': pname}
    for a in acts
    for (team, action, pname) in a.actions
]
pd.DataFrame(rows).to_csv(
    'data/outputs/transactions_history.csv',
    mode='a', header=..., index=False,
)
```

Once both files have ≥6 closed periods of coverage (~mid-July 2026),
re-run this validation: incremental projection update from each
transaction, residual MAE before vs after, with per-event Δ-attribution.
