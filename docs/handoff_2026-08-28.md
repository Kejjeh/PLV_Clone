## 1. Issue #52 — rp3 models IL absences but not OPTION absences

**Status:** open, unstarted, deliberately.

The issue sets its own bar: a **matched-control test before any feature work**.
That is the right bar and the same one gotcha #14 rests on — excess |ΔK-BB%|
over matched same-position controls was ~0 for IL_SHORT / IL_MED / TRADE /
IL_LONG, all n.s. An option stint looks like it should carry signal for exactly
the reasons an IL stint does, which is why it needs the control arm *first*.

Building the panel **is** the job, and the panel's substrate is absent here.
Running it against a checkout with no `rolling_pitchers_2018_2026.csv` would be
a different and worse study, not a shortcut.

**Carry these in rather than rediscovering them:**

- **Which significance bar applies.** An option stint *gives* the split point,
  so judge at **z > 1.83** (one test) — NOT the searched-split bar of SP 2.58.
  Confusing the two is how 39% of pitcher-seasons clear a threshold by
  construction (gotcha #14).
- **Assert `1/(B+1) < q/M` before believing any permutation null** (trap #17b).
  With the pitcher-season counts involved this is easy to violate and yields a
  guaranteed null that reads like a finding.
- **Report one-row-per-player-season next to any pooled result** (trap #17
  corollary). The prior RP boom study had 509 records from 14 pitchers.
- Nothing regime-derived may move rh3/rp3/rprs2 without `/validate-feature`
  (don't-do #1, Rule 9: the baseline must include ALL existing production
  features).

**Route:** `/validate-feature` with a pre-registration file in
`data/research/validation_runs/`.

## 2. Issue #54 — counterfactual pairing: the structural half

**Status:** open. The *fixable* half shipped in PR #88; the binding constraint
is a workflow habit, not a code path.

**What I measured** (posted to the issue), across every record in
`data/research/decisions`:

```
records: 3101   with a counterfactual: 10
  no_counterfactual       3091      (99.7%)
  id + name                  7
  name only                  2      <- recovered by PR #88
  neither                    1
  lookup_failed_side=*       0
```

This **rules out** both prior diagnoses. Not the rejected leg's actuals (the
original theory), and not a fetch failure (the post-#76 theory — zero records
carry `lookup_failed_side`). The constraint is that 99.7% of decisions never get
a surface attached at all, so there is nothing to pair. Settling faster, fixing
fetches, and waiting for windows all leave that untouched.

That is CLAUDE.md's workflow rule not being followed: *run the optimizer or
`/matchup-leverage` BEFORE executing a move; a move made when no surface existed
can never be graded.* It matches the 2026-07-29 dry run finding all 21 recent
moves unattributable for the same reason.

**Two directions, neither built — and the first is a product decision, not a
refactor, which is why I stopped:**

1. **Make the pre-move surface unavoidable.** e.g. `/churn-plan`'s
   DID-IT-EXECUTE step refusing to mark a move done without a `dpwin_history`
   row to attribute it to. This changes how Josh is allowed to work; it needs
   his agreement, not a PR.
2. **Retro-attribute from `dpwin_history.parquet`**, which holds every evaluated
   candidate including rejected ones. `reconcile_decisions.py` already joins
   executed ESPN transactions back to the motivating surface. The open question
   is whether a surface existed *at execution time* — for these 3,091 it
   evidently did not, so this may recover little. **Needs ESPN credentials** to
   test against live transactions.

Either way the n≥30 gate on §9 is many decisions away and will be paced by how
many future moves get a surface, not by the settler.

## 3. PL cache `week` field is not used in the staleness decision

**Status:** open, flagged in PR #89, not taken.

`_cache_is_stale(fname, fetched)` judges on the calendar. The cache also records
the **resolved edition `week`**, and `build_pl_cache.py`'s own comment documents
the failure that closes:

> on 2026-08-18, weeks 22 and 21 both 404'd and week 20 served — yet the payload
> was stamped 2026-08-12 exactly as the previous week-19 pull had been. Two
> different editions carrying an identical `fetched` date made the cache look
> current while it sat a full week behind.

Judging on the recorded `week` rather than the stamp closes that. **I left it
because `_cache_is_stale` has 28 call sites across 10 modules** — a signature or
semantics change there is exactly the don't-do #18 blast radius, and it wants a
deliberate sweep rather than a drive-by.

**If you take it:** add an optional `week=` argument with the calendar path
unchanged as the default, so no existing caller moves. Guard with
`tests/test_pl_staleness_cadence.py`, which already pins the cadence contract
and the publish-hour boundary.

### Live PL cache state at handoff

SP        ok     current (latest live Mon edition 2026-08-24 already cached)

**Do not try to "fix" H by refetching.** Verified against Pitcher List's WP API:
the newest Top 150 Hitters edition is **Week 20, published 2026-08-14** — which

## 5. Judgment calls I made that you may want to revisit

Both are flagged in their PRs; neither is load-bearing enough to block anything.

- **CLAUDE.md ceiling is 320, not the ~200 the file asked for** (PR #88). 33
  numbered rules at one line each is ~110 lines before the league constants, the
  scoring formulas or the model table. A ceiling the file cannot meet is one
  that gets ignored — which is how it reached 635. Currently **319 against the 320
  ceiling — one line of headroom**, because don't-do #18 was added after the
  extraction. `tests/test_claude_md_budget.py` ratchets it, so the next rule
  added inline WILL fail CI. That is the intended behaviour (the fix is to
  extract, not to raise the ceiling), but it means the very next CLAUDE.md edit
  has to do the extraction work. Worth knowing before you hit it.
- **`cap_excess_starts` still ranks unresolved starts last** (PR #87, issue
  #61). I closed the *silent* half — an unmatched SP is now flagged
  `rate_resolved=False` and surfaced by `unresolved_starts()` — but did not
  change what the function *decides*, because whether a filler zero should sort
  last, first, or be excluded is a roster-strategy call, not a bug fix.

## Postscript — a defect I introduced and fixed while writing this

that **duplicated `tests/test_pl_cadence.py`**, which already owned the cadence
contract: the publish-hour boundary, the rolling streamer window, and

Removed, with a SCOPE note in the file's docstring pointing at the sibling that
owns the contract. What remains there is only what `test_pl_cadence` cannot
cover: that `test_triangulate` delegates rather than re-deciding, the specific
divergence the flat rule got wrong, and the helper's contract.

Two things worth carrying from that: the rule is easy to violate even while
holding it in mind, and a `grep -rn "<the function>" tests/` before adding any
guard file would have caught it in seconds.
